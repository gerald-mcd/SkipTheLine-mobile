Step 1 of 3 · Define the Invention

This Is Exactly How SkipTheLine Works

A complete end-to-end description of the SkipTheLine system — from the moment a venue enters the database to the moment a user receives a real-time wait time alert. This document describes the entire process, including how data enters the system, how it is validated and processed, how results are delivered, and how the system generates ongoing analytical value. The attorney — not us — will determine which elements are novel and potentially protectable.

Phase A

System Population — Before Users Arrive

Before any user opens the app, the system must already contain venues. SkipTheLine uses a three-source pipeline to populate and maintain the venue database.

1
Automated Google Places Grid Import

Before launch, a script queries the Google Places API by venue category and city using a geographic grid pattern. Every relevant business in Miami is automatically imported into the Supabase database. This produces approximately 3,500 venue records before any user ever opens the app.

  • Data captured per venue: name, address, GPS coordinates, category, hours, phone number, photo references
  • Google Popular Times data used as baseline wait time fallback while crowdsourced data accumulates
  • One API key from Google Cloud covers Maps SDK, Places API, and Maps API
2
Business Self-Registration (B2B Layer)

A business owner finds their venue listing (already in the database from the Google import) and claims it. They verify ownership, manage their profile, and optionally manage their own queue data. This is the paying SMB subscriber product — subscribers gain access to the business analytics dashboard.

3
User-Submitted Venues

If a user tries to report a wait at a business not in the database, they can submit it directly through the app (name, category, address). The submission enters a review queue and goes live after approval. This catches new businesses, pop-ups, and anything missed by the Google Places import.

Phase B

User Onboarding & Account Creation

1
Authentication

User opens the app and reaches the Welcome screen. Authentication options: email/OTP, Apple Sign-In (OAuth), or Google Sign-In (OAuth). A Supabase session is created upon successful authentication.

2
User Profile Initialization

A user record is created in the database with initial values. The trust score system initializes at this point:

  • trust_score: 100 — every new user starts with full trust
  • report_count: 0 — lifetime report counter
  • flagged_count: 0 — number of reports flagged as suspicious
3
Permissions

Location permission requested: "While Using" only (Phase 1 — not "Always Allow"). Push notification permission requested. Graceful degradation — the app functions fully without location; ambient features require it. Expo push token captured and stored on the user record for targeted notifications.

Phase C

Venue Discovery & Browsing

1
Venue List (Home Tab)

The Home screen queries the Supabase database for launched venues. The user can filter by category (12 categories: Restaurants, Barbershops, DMVs, Attractions, Landmarks, Nightclubs, Dayclubs, Healthcare, Retail, Grocery, Entertainment, Government), search by name, or filter to only venues with short waits (≤15 minutes). Results paginate at 20 per page. Each venue card displays the current wait time color-coded by severity.

Wait time color language: Gray = no data · Green = 0–10 min · Orange = 11–25 min · Red = 26–45 min · Dark red = 45+ min
2
Map View (Discover Tab)

The Map tab displays venues as geographically positioned pins on an interactive map. Each pin is color-coded by current wait time using the same color language as the list view. Venues with reports less than 5 minutes old display a pulsing ring animation on their pin — a live data signal visible to users at a glance. A bottom sheet slides up to display a sorted venue list (ordered by number of live reporters).

3
Venue Detail

Tapping any venue opens the Venue Detail screen, which displays:

  • Current wait time (large, color-coded by severity) with a severity label: SHORT / MODERATE / LONG LINE
  • Sparkline chart showing wait trend over time
  • Average (typical) wait time from historical data
  • Number of reports and last updated time
  • Hours of operation (tappable, expands to full week)
  • Recent reports: reporter name (or "Someone nearby"), report type, time elapsed, wait minutes
  • Photo carousel, vibe tags, reviews with rating breakdown
  • Directions button (deep-links to OS default maps app), Website button, Report Wait button
Phase D

Wait Time Report Submission

1
Report Initiation

The user taps the Report FAB (floating action button at the center of the tab bar) or the "Report Wait" button from a Venue Detail screen. If arriving from Venue Detail, the venue is pre-selected via route parameter. Otherwise, the user selects a venue through the Venue Picker (searchable by name and category).

2
Report Type Selection

The user selects the type of wait being reported. This is a distinct, structured data field — not a free-text note:

  • Walk-in — general queue, no reservation
  • Reservation — wait despite holding a reservation
  • VIP — VIP entry queue at nightclubs, events
  • Guest list — guest list entry queue

These distinctions are critical: a 45-minute walk-in wait and a 0-minute reservation wait at the same venue are different data points that cannot be averaged together meaningfully.

3
Wait Time Entry

User selects from preset options (No wait, 5 min, 15 min, 30 min, 45 min, 60 min) or enters an exact number (0–180 minutes). An optional note can be added (140 character maximum with counter). A points preview card shows the expected SkipPoints reward for a valid submission.

4
Report Record Created

On submission, a report row is written to the database containing:

  • venue_id, user_id, wait_minutes, report_type, optional note
  • timestamp (server-side)
  • user GPS coordinates at time of submission
  • anomaly_score (set to null, computed in next phase)
  • location_verified (set to null, computed in next phase)
  • flagged: false (default)
Phase E

Report Validation & Anomaly Detection

Immediately upon report insertion, a Supabase Edge Function is triggered. This is the fraud and quality control layer — every single report goes through this process before it can affect the displayed wait time.

1
Trust Score Pre-Weighting

Before any detection signals are evaluated, the submitting user's trust_score is retrieved. Reports from users with degraded trust scores are pre-weighted down before the anomaly check runs. A new user with trust_score 100 gets full weight; a user with trust_score 40 gets 40% weight as a starting point.

2
Six Detection Signals Evaluated
  • Statistical outlier — report deviates more than 2× from the median of recent reports at the same venue
  • Velocity abuse — same user submitted 3 or more reports at the same venue within 30 minutes
  • Location mismatch — submitted GPS coordinates do not place the user within the expected proximity of the venue
  • New account spam — account is less than 24 hours old and is submitting high-volume reports
  • Pattern anomaly — user historically always reports extreme values (always 0 minutes or always 90+ minutes) across many different venues
  • Coordinated attack — multiple accounts sharing the same IP address or device fingerprint are reporting the same outlier value at the same venue
3
Anomaly Score Computed

The Edge Function computes an anomaly_score of 0–100 for the report. 0 = clean. 100 = highly likely fraudulent. This score is stored on the report row and is the primary input to the response tier decision. The location_verified boolean is also set based on the GPS proximity check.

4
Response Tier Applied
Tier Trigger Action
Tier 1 · Soft Flag Mildly elevated anomaly score Report included in calculation at reduced weight. SkipPoints awarded at reduced rate.
Tier 2 · Hard Flag High anomaly score Report excluded from calculation entirely. flagged = true on report row. SkipPoints award frozen for this submission.
Tier 3 · Ban Repeat offender pattern Account suspended from reporting. Flagged for manual review. User's trust_score degraded.
5
Trust Score Updated

If the report is clean (Tier 0): SkipPoints awarded, report_count incremented, trust_score maintained. If flagged: flagged_count incremented, trust_score degraded proportionally. A user's trust_score degrades over time with bad reports, meaning their future reports are pre-weighted down before the anomaly check even runs — a compounding quality signal.

Phase F

Wait Time Calculation

1
Report Aggregation

The wait time engine aggregates all non-flagged reports for the venue. Only reports with flagged = false and anomaly_score below the threshold are eligible for inclusion.

2
Time-Decay Weighting

Every eligible report is weighted based on how old it is at calculation time. Newer reports carry more weight; older reports decay toward zero and are eventually expired:

Time Since ReportWeight AppliedVisualization
0–10 minutes100%
20 minutes70%
30 minutes40%
45 minutes15%
45+ minutesExpired
removed

This ensures the displayed wait time reflects current conditions, not stale historical data.

3
Event Context Applied

If an active event is attached to the venue (e.g., "Art Basel week," "Heat game night"), the venue's crowd_multiplier_estimate is factored into the wait time prediction. A venue during Art Basel with a multiplier of 2.5× behaves differently in the model than the same venue on a normal Tuesday. The event badge is also surfaced on the map pin and venue card so users understand why the wait is elevated.

4
Result Published

The weighted average is computed and the current_wait_minutes field on the venue record is updated. If the new wait is 30% lower than the previous value, or crosses a psychological threshold (e.g., 45 min → 20 min), a wait_drop_event record is created to trigger alerts.

Phase G

Information Delivery to Users

1
Real-Time Update (In-App)

Supabase Realtime pushes the updated wait_minutes to all app instances currently viewing that venue. Venue cards, detail screens, and map pins update instantly without requiring a manual refresh. The rate limiter is set to 10 events per second.

2
Wait Drop Proximity Alert (Push Notification)

When a wait_drop_event is created, the system evaluates whether to fire a push notification. Three conditions must all be true:

  • User is within 0.3 miles (walking) or 1.5 miles (driving) of the venue
  • Wait dropped more than 30% OR crossed a psychological threshold (e.g., 45 min → 20 min)
  • User showed prior interest — viewed the venue in the last 4 hours, favorited it, or previously reported there

If conditions are met, the push notification delivers pure value: venue name, old wait → new wait, and distance. No question asked. One optional action: "Open in Maps."

Delivery mechanism: silent push notification wakes the app for 30 seconds; app checks current location in that window; if user is still in range, the visible notification fires; if out of range, it discards silently.
3
Arrival Nudge (Ambient Reporting Trigger)

When a user is physically near a venue, the system proactively prompts them to report. Trigger conditions:

  • User GPS within 80 meters of venue
  • Dwell time exceeds 3 minutes (eliminates walk-bys)
  • First detection at this venue today (prevents repeat prompting)

To reduce false positives, the system uses intent correlation — multiple signals are combined before the nudge fires:

  • Dwell > 8 min alone → nudge fires
  • Dwell > 3 min + user viewed venue in app today → nudge fires
  • Dwell > 3 min + user navigated to venue → nudge fires
  • Dwell < 3 min + no prior signals → no nudge

The nudge UI offers one-tap reporting: No wait / ~15m / ~30m / 45m+ / Don't know yet. If "Don't know yet" is selected, a follow-up fires at 15–20 minutes of dwell time.

4
Post-Visit Nudge (Historical Reporting)

8–12 minutes after a user leaves a venue's proximity zone, a local notification fires prompting a post-visit wait time report. These reports are handled differently from real-time reports: they are labeled as historical, time-decay is applied from the moment of visit (not submission), and they are displayed with an honest timestamp ("Reported 28 min ago — may not reflect right now"). Post-visit reports never display as the current wait time without decay applied.

5
Live Activity Feed (Explore Tab)

The Explore tab surfaces a real-time activity feed showing recent wait drop events, user reports, and venue updates. Users can filter by type: all activity / wait drops / reports / venues / system. Feed items link directly to venue detail screens.

Phase H

Gamification & User Engagement

1
SkipPoints Award

Every valid, non-flagged report earns the submitting user SkipPoints. Flagged reports earn zero points. This structurally ties the reward system to data quality — bad actors are not only excluded from the calculation but also receive no reward benefit. Points accumulate on the user record.

2
Tier Progression & Leaderboard

Users progress through named tiers as SkipPoints accumulate. Weekly XP is tracked separately from lifetime points. A weekly leaderboard snapshot job ranks users by weekly activity. Top reporters in a geographic area are surfaced to venues — a B2B differentiator where paying venues can offer perks to their top local reporters.

3
Badges & Quests

An Edge Function evaluates badge unlock criteria after every report submission. Badges reward behavioral milestones (first report, reporting streak, reporting at new venue types, etc.). Quests are multi-step challenges with progress bars — completing a quest awards a point bonus. Both badges and quests are designed to encourage diverse, high-quality reporting behavior across multiple venue types and time periods.

4
Rewards Redemption

Accumulated SkipPoints can be redeemed for partner rewards (discounts, offers). Points are deducted from the user record and a unique reward code is generated upon redemption.

Phase I

Historical & Analytical Value

1
Permanent Report Archive

Every report is stored permanently with its full metadata: venue_id, user_id, wait_minutes, report_type, timestamp, anomaly_score, location_verified, trust_score at time of submission. This builds a time-series dataset of wait conditions per venue per day, time of day, day of week, and event context.

2
Historical Pattern Calculation

The typical_wait_minutes field on each venue is computed from historical report data. Users see this displayed as "Average wait" on the venue detail screen — allowing comparison between the current live wait and the historical norm for that time of day.

3
B2B Analytics Dashboard (SMB Subscribers)

Paying venue subscribers gain access to a business analytics dashboard built from the same underlying report data. The dashboard surfaces: who is waiting and when, report frequency by time of day and day of week, peak wait periods, conversion analytics (how many users who viewed the venue visited), and comparison to category averages. This is the primary B2B revenue product.

4
Community Impact Tracking

The system pre-computes a "people helped" statistic — tracking how many other users received wait information downstream from each reporter's submissions. This is displayed on user profiles to reinforce the community contribution loop.

Phase J · Planned — Sufficiently Developed to Describe

Voice AI Agent

1
Conversational Interface

A user taps a microphone button and speaks naturally. The voice layer is a full back-and-forth conversation — not a one-shot command. The stack: Vapi (orchestration, turn-taking, interruption handling) → Whisper (speech-to-text) → Claude Sonnet (LLM reasoning over live SkipTheLine data) → ElevenLabs (text-to-speech response).

2
Function Calls Against Live Data

The LLM layer can call structured functions against the SkipTheLine database in real time:

  • getWaitTime(venueId) — retrieves current wait for a named venue
  • reportWait(venueId, minutes, reportType) — submits a wait report by voice, awards SkipPoints automatically
  • setWaitDropAlert(venueId, threshold) — sets a personalized wait drop alert ("tell me when LIV drops under 20 minutes")
  • addToCalendar(venueId, time) — adds a venue visit to the user's device calendar via the Expo Calendar API
Phase K · Planned — Sufficiently Developed to Describe

BLE Beacon Detection (B2B)

Paying SMB subscribers receive BLE (Bluetooth Low Energy) beacon hardware ($15–30 per device) installed in their venue. When a user's phone detects the beacon's Bluetooth signal, the app knows the user is physically present — without requiring "Always Allow" location permission (Bluetooth permission only). This triggers the arrival nudge automatically and enables venue-verified visit detection. For the B2B subscriber, beacon data improves the accuracy of their analytics dashboard and generates more reliable wait time data for their venue. Beacon hardware becomes a B2B sales feature: subscribers get smarter, more accurate wait data because physical presence is confirmed by Bluetooth rather than inferred from GPS proximity.

Step 2 of 3 · Identify Differentiators

What SkipTheLine Does That Others Don't

For each item below: what it is, how it works, why it is different from existing approaches, and whether it is part of a larger process. These are factual descriptions — not legal conclusions. The attorney will determine which elements are novel and potentially protectable.

01
Anomaly Detection + Per-User Trust Score System

What it is: A two-layer fraud and quality control system. Every report is scored 0–100 for likelihood of being fraudulent (the anomaly score). Separately, every user carries a persistent trust score (0–100) that degrades when their reports are flagged and recovers with reliable reporting.

How it works: Six detection signals are evaluated per report: statistical outlier (>2× median deviation), velocity abuse (3+ reports at same venue within 30 min), location mismatch (GPS doesn't place user near venue), new account spam (<24 hrs old), pattern anomaly (always extreme values across many venues), and coordinated attack (same IP/device fingerprint). The trust score pre-weights the report before these signals are evaluated — a low-trust user's report starts at reduced weight regardless of the individual report's signals.

Why it's different: Google's Popular Times data is algorithmic from historical foot traffic — it has no per-report validation and no per-user trust model. Yelp reviews are moderated by editors and crowd-flagging, not real-time algorithmic scoring. No existing crowdsourced wait time system applies a compounding per-user trust model where a user's history of fraudulent submissions reduces the influence of their future submissions before those submissions are individually evaluated.

Part of a larger process: Yes — this is Phase E of the complete process, and its outputs directly feed Phase F (wait time calculation). A report that scores Tier 2 never affects the displayed wait time. The trust score feeds back into Phase E for every future report from that user.

Is this unique? How does it work? Part of a larger process
02
Time-Decay Weighted Wait Calculation

What it is: A mathematical weighting formula applied to all eligible reports when computing the current displayed wait time. Older reports carry less weight; reports expire completely at 45 minutes.

How it works: Each report's contribution to the weighted average is multiplied by its decay factor: 100% if 0–10 min old, 70% at 20 min, 40% at 30 min, 15% at 45 min, 0% (expired) beyond 45 min. The final displayed wait is the weighted mean of all eligible non-flagged reports.

Why it's different: A simple average of reports would cause stale data to persist and drag the displayed wait toward old conditions. Most crowd-sourced systems either use the most recent single report (volatile) or a straight average (lags behind reality). Time-decay weighting is a specific design decision to make the displayed number reflect the current moment, not the recent past.

Part of a larger process: Yes — this is the core of Phase F. Its output is the wait time that users see, that alerts are based on, and that the B2B analytics dashboard reports.

Is this unique? How does it work? Part of a larger process
03
Report Type Specificity — Walk-in / Reservation / VIP / Guest List

What it is: A structured, required field on every wait time report capturing the type of entry being reported — not free text, but a defined category from a fixed set.

How it works: At report submission, the user selects one of: Walk-in (general queue), Reservation (wait despite holding a reservation), VIP (VIP entry queue), Guest list (guest list entry). This field is stored on the report record and is used to segment wait time data by entry type.

Why it's different: A 45-minute walk-in wait and a 0-minute reservation wait at the same restaurant are completely different data points — averaging them together produces a meaningless number. No existing public wait time product captures this distinction as structured data. For nightclubs and dayclubs specifically, this distinction (VIP vs. guest list vs. general) is the difference between useful and useless wait information.

Part of a larger process: Yes — report type is captured in Phase D and stored with the report record, enabling downstream filtering and segmentation in Phases F and I.

Is this unique? How does it work? Why is it different?
04
Gamification Loop Structurally Tied to Data Quality

What it is: A points, tier, badge, and quest system where rewards are structurally withheld from fraudulent or low-quality reports — not just manually moderated after the fact.

How it works: SkipPoints are only awarded when the anomaly detection system clears a report (Tier 0 or 1). A Tier 2 (hard-flagged) report earns zero points — the SkipPoints award is frozen at the Edge Function level before it is issued. A user who submits bad reports not only fails to influence the wait time, they also fail to earn rewards.

Why it's different: Waze awards points for reporting but has no structural linkage between report quality and reward. A bad actor on Waze can earn driving points while submitting false hazard reports. SkipTheLine's architecture makes the reward system and the data quality system the same system — one Edge Function output determines both.

Part of a larger process: Yes — this spans Phases E and H. The anomaly detection output directly gates the gamification output.

Is this unique? Why is it different? Part of a larger process
05
Intent-Correlated Arrival Nudge

What it is: A system that detects when a user is physically present at a venue and prompts them to report — but uses multiple intent signals in combination, not proximity alone, to determine whether to fire the prompt.

How it works: Proximity (80m radius) and dwell time (>3 min) are necessary but not sufficient. The system also evaluates: whether the user viewed this venue in the app today, whether they navigated to it via the app, and whether this is their first detection at this venue today. Multiple signal combinations determine whether the nudge fires. This prevents the system from prompting users who merely walked past a venue.

Why it's different: Standard geofence implementations fire on entry/exit only, with no dwell or intent model. The combination of proximity + dwell + prior intent signals as a composite trigger — without requiring "Always Allow" location permission — is a deliberate architectural design.

Part of a larger process: Yes — this is Phase G, Step 3. The nudge's output is a user-initiated report that then flows through Phase D → E → F.

Is this unique? How does it work? Part of a larger process
06
Event Tagging with Crowd Multiplier Estimate

What it is: A structured event data model that attaches named events to venues with a quantified crowd impact estimate, which the wait time engine uses to adjust predictions when an event is active.

How it works: Events are records in the database with: venue_id, event_name, event_type, start_time, end_time, and crowd_multiplier_estimate. When an event is active, the wait time engine multiplies expected crowd by the multiplier (e.g., 2.5× for Art Basel). Events can be system-generated (from a public events API), business-submitted (through the SMB dashboard), or user-confirmed (threshold of user event tags creates a confirmed event). The map pin and venue card display an active event badge.

Why it's different: Google Maps shows business hours and ratings but has no model for event-driven wait time adjustment. A static wait time average is meaningless during a major event. The crowd_multiplier_estimate is a quantified prediction input, not just a label.

Part of a larger process: Yes — event context is applied in Phase F, Step 3 of the wait time calculation.

Is this unique? How does it work? Part of a larger process
07
B2C + B2B Dual-Loop Data Model

What it is: A system architecture where consumer-submitted wait time data is simultaneously the product (displayed to consumers) and the input (sold as analytics to businesses). The two markets reinforce each other rather than operating as separate systems.

How it works: Every consumer report that passes validation is stored permanently. The same record that contributes to the displayed wait time also contributes to the venue's analytics dashboard in the B2B product. A venue with more consumer reporters generates more accurate analytics for the business subscriber. The B2B subscriber's claimed venue also gains enhanced accuracy because the business can add their own data (hours, event schedule, entry types) that improves the context of consumer reports.

Why it's different: Yelp has reviews (B2C) and business tools (B2B) but they are largely separate systems. Google Maps has user reviews and Google Business Profile but wait times are algorithmic, not the same crowdsourced loop. SkipTheLine's architecture makes B2C data quality improvements directly improve B2B analytics, and B2B subscriber data improvements directly improve B2C displayed accuracy.

Is this unique? How does it work? Why is it different?
08
Three-Source Venue Seeding Pipeline

What it is: A structured system for populating the venue database through three distinct pathways: automated import, business self-registration, and user submission — with defined data handling for each path.

How it works: (1) Google Places API grid import: automated script queries by category and city before launch, imports ~3,500 venues with structured fields. (2) B2B self-registration: business owner claims their existing database record, verifies ownership, gains SMB subscriber access. (3) User submission: if venue not in database, user submits a form that enters a review queue before going live. Each source has different trust and completeness characteristics; the database schema accommodates all three.

Why it's different: Most local business data products rely on a single source. The three-source design solves the cold-start problem while building a feedback mechanism for ongoing database accuracy.

Is this unique? How does it work? Part of a larger process
09
Honest Timestamp & Source Transparency

What it is: A display standard where every wait time shown to users includes: how many people reported it, how long ago, and whether it is a live or post-visit report. Post-visit reports are explicitly labeled and have time-decay applied before display.

How it works: Live reports (user physically present, confirmed by dwell + GPS) display with a green LIVE badge. Post-visit reports (submitted after leaving) display with an honest elapsed time label ("Reported 28 min ago — may not reflect right now") and never display as the current wait time without decay applied. The distinction between live and historical is surface-level in the UI, not hidden in the algorithm.

Why it's different: Google Popular Times shows a historical average with no individual report transparency. Most crowd-sourced systems aggregate and display without revealing the age or confidence level of the underlying data. SkipTheLine's display standard makes data provenance visible to the end user.

10
BLE Beacon-Confirmed Visit Detection (B2B)

What it is: A B2B hardware+software system where Bluetooth beacons installed at subscribing venues enable phone-side presence detection without requiring "Always Allow" GPS permission.

How it works: Paying SMB subscribers receive beacon hardware. The beacon broadcasts a Bluetooth signal; the user's phone detects it via the Bluetooth permission (less invasive than Always location). Detection triggers the arrival nudge automatically — more reliably and with less user friction than GPS-based detection. The beacon-confirmed visit data flows into the subscriber's analytics dashboard as a verified visit signal.

Why it's different: Traditional geofencing requires Always location permission, which users resist granting. Bluetooth beacon detection achieves the same physical presence confirmation through a separate, less sensitive permission channel. This is a hardware+software integration specifically designed to improve data accuracy at subscribing venues without requiring the most invasive location permission tier.

Trust Score SystemDesigned
Per-user trust_score (0–100, starts at 100). Pre-weights report before anomaly signals evaluated. Degrades with flagged reports. Maintained/recovered with clean reports. Stored on user record.
Time-Decay Wait EngineDesigned
Aggregates non-flagged reports per venue. Applies decay weights by age (100%/70%/40%/15%/expired). Computes weighted average. Writes to current_wait_minutes on venue record.
Event Context ApplicationDesigned
If active event attached to venue, crowd_multiplier_estimate applied to wait time prediction during calculation phase.
SkipPoints Award LogicDesigned
Edge Function awards points only after anomaly check clears report. Tier 2 (hard flag) freezes award. Points added to user record. Points award is a direct output of the anomaly decision.
Badge Criteria CheckDesigned
Edge Function evaluates badge unlock criteria after every valid report. If criteria met, badge record created for user. 17 badge types defined.
Historical Pattern ComputationDesigned
typical_wait_minutes computed from historical report archive per venue, segmented by time of day and day of week. Used for "Average wait" display and B2B analytics baseline.
Leaderboard Snapshot JobDesigned
Weekly batch job ranks users by weekly report activity. Snapshot stored for leaderboard display. Resets weekly XP counter.
Intent Correlation (Arrival Nudge)Designed
Composite signal evaluation: GPS proximity (80m) + dwell time (>3 min) + prior venue view + navigation history + first detection today. Multiple conditions required before nudge fires.
LLM Function Routing (Voice)Designed
Claude Sonnet processes natural language query, routes to appropriate function call (getWaitTime / reportWait / setWaitDropAlert / addToCalendar), returns spoken response via ElevenLabs TTS.
How Information Is Updated
Real-Time PushBuilt
Supabase Realtime pushes updated current_wait_minutes to all app instances viewing that venue. Rate: 10 events/second. No manual refresh required.
Wait Drop DetectionDesigned
After each wait calculation, new value compared to previous. If drop >30% or crosses psychological threshold (e.g., 45→20 min), wait_drop_event record created. Triggers alert pipeline.
Trust Score DecayDesigned
User trust_score decremented when report is flagged. Incrementally recovers with clean submissions. Updated on user record after every report processed.
Venue Data UpdatesBuilt

Event StatusDesigned
Events activate/deactivate based on start_time and end_time. Active event badge appears/disappears on venue card and map pin automatically.
